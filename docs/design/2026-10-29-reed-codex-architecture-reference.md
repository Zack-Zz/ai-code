- 产品是本地优先的 Agent 研发工作台，以任务推进需求、设计、开发、验证，关联会话、分支、工作区、文档与交付；不扩展成完整 IDE 或另一个通用 Agent 引擎。

- Task、StageRun、AgentAttempt、Acceptance 和 CompletionDecision 各有语义。执行结束不等于验收，云效状态不替代本地阶段。
- 云效由 Core 的官方 CLI 适配负责；HostAdapter、AgentExecutor、ProviderConnector 分开。MCP 是可选适配，不提供额外数据库权威或隐含会话控制权。

## 3. 项目结构：按职责分包，按运行位置装配

### 3.1 Codex 的结构启示

精简目录如下，仅用于导航，不代表完整模块或严格单向依赖图：

```text
codex/
  codex-rs/
    cli/                         用户命令与入口装配
    tui/                         终端界面
    exec/                        非交互执行入口
    app-server/                  应用请求、事件与运行时装配
    app-server-client/           共用客户端
    app-server-protocol/         对外契约与生成物
    app-server-daemon/           独立服务管理
    core/、core-api/             Agent 运行能力与公开门面
    thread-store/、rollout/、state/
                                 存储边界、历史与状态
    exec-server/                 文件/进程/执行环境能力
    ext/、plugin/、core-plugins/ 内部扩展与插件集成
    config/                      配置来源、合并与版本
  sdk/                           TS/Python 接入
  codex-cli/                     npm 分发与原生程序启动包装
  scripts/、docs/                 工程工具与资料
```

crate 是编译/依赖单元，不自动成为常驻进程。Reed 也应分别表达源码包、可执行程序、安装制品和实际运行进程，不能把它们画成同一层。大量模块拆分是 Codex 当前规模和历史的结果，不是 Reed 初版需要的目录数量。

### 3.2 映射到 Reed 原工程结构

下表复用原设计中的计划目录，不新增另一套工程布局；同一职责没有独立复用/依赖边界时，先作为模块，不要求立即拆包。

| 原计划位置 | 可细化的工程责任 | 依赖限制 |
| --- | --- | --- |
| `apps/core` | 进程入口、配置/存储/连接器装配、生命周期、客户端准入 | 不承载 React 或 Tauri；领域规则不散落在请求路由 |
| `apps/desktop` | Tauri 窗口、系统桥、可信发现/启动和共享 UI 容器 | 不执行数据库迁移、云效写入或阶段判定 |
| `packages/domain` | 范围、阶段、验收、完成及有类型关系的规则 | 不依赖宿主 SDK、传输协议、CLI 参数或 SQLite 驱动 |
| `packages/application` | 业务用例、事务、授权范围、操作回执与端口 | 调用领域和端口，不接收任意 shell 字符串 |
| `packages/contracts` | Wire DTO、错误、事件、能力及生成说明 | 不暴露数据库行、凭据明文或运行时内部管理器 |
| `packages/client` | 握手、请求关联、订阅、重连、事件缺口与类型化错误 | 连接既有 Core，不拥有第二份业务数据库 |
| `packages/infrastructure` | 存储、文档、Git/worktree、系统资源等适配 | 实现应用端口；不从客户端读取当前焦点来决定业务目标 |
| `packages/connectors`、`packages/execution` | 来源与执行能力实现 | 来源状态不进入通用领域；宿主执行和独立执行所有权分开 |
| `packages/ui` | 共享交互、视图模型与有限 ShellBridge | 不导入 Tauri/特定宿主 SDK，不直接访问持久业务存储 |
| `ai-code/plugins/reed` | 原生宿主入口、权限/事件翻译、固定发行输入 | 不复制 Core 应用用例或升级/安装器 |

客户端库的源码权威仍在 Reed，ai-code 消费固定版本/哈希的制品；跨仓开发相对路径只能是显式开发方案，不能进入正式包。源码包可共享，客户端和 Core 安装版本不要求同号，协议兼容关系单独记录。

### 3.3 不复制的结构

不因参考 Codex 引入 165 个模块、云控制平面、通用执行环境集群或完整模型循环。`core-api` 的大量转导出、客户端的 `legacy_core` 兼容入口和存储接口的实现逃逸不适合作为 Reed 默认模式；只开放明确用例、查询与有限端口，特殊内部能力有独立范围及调用者。

## 4. 协议契约：同一语义，多种传输

### 4.1 四种边界不能混为一谈

| 边界 | 例子与责任 |
| --- | --- |
| 领域模型 | Task/StageRun/Acceptance 的业务语义与不变量 |
| 进程内应用端口 | 查询任务、申请开始阶段、记录执行观察等用例；供 Core 内部装配 |
| 对外应用契约 | 稳定目标、固定输入、expectedRevision、操作回执、查询投影和事件 |
| 传输与宿主桥 | 私有 IPC、可选 loopback、MCP 或宿主消息桥的编码、连接和权限翻译 |

Codex 的内嵌路径保留应用协议语义，值得学习；Reed 不因此必须使用 JSON-RPC，也不必将所有业务动作变成 MCP 工具。传输选择在 P0 结合平台与宿主可用性确定，各通路最终进入同一 Core 用例与授权检查。

Rust 的公开 trait/struct、TypeScript 的接口、Tauri command 和网络 Wire DTO 都不是天然同一契约。Core 内部对象不直接序列化给页面，Wire DTO 按公开含义建模，转换放在入口/投影层。

### 4.2 单一契约来源与生成

候选要求是：一份版本化定义产生运行时校验、TS 客户端类型和必要 schema，生成物由门禁核对。以当前 TS Core 为基线，先评估适合现有工程的权威 schema 方式；若未来采纳 Rust Core，再评估从 Rust 类型导出。两条路线互斥评估，不同时维护两份可手工编辑的协议权威。

明确缺省值、缺失与 null 的区别、枚举未知值、路径表示、数字/时间精度、分页范围和错误语义。声明 TS 类型不等于有运行时校验；反序列化成功也不证明权限、状态转换或证据有效。认证、输入、业务和来源检查各有责任。

稳定/实验字段及方法单独列能力。新增可选字段需老客户端容忍，未知有副作用动作不得猜测执行；破坏性变化须明确版本协商与拒绝行为。生成物对齐测试不能单独证明新旧组合兼容，仍需固定版本客户端与服务端的组合验收。

### 4.3 请求、业务操作、执行与事件身份

| 身份 | 范围与限制 |
| --- | --- |
| 传输请求 ID | 匹配一条连接/通路中的请求与响应；重连可能变化，不证明业务未执行 |
| 持久 requestId / operationId | Orca 参考中的稳定意图与 Core 接纳记录；重传、恢复和未知效果核查的依据 |
| Task/StageRun/AgentAttempt | 业务任务、固定阶段输入与一次执行，不按连接或聊天消息新建 |
| 原生 session/thread/turn | 执行器/宿主范围中的真实运行对象；独立 app-server 新会话不冒充桌面已有会话 |
| serviceEpoch / 绑定代际 | 核验当前服务和执行绑定；换代不删除历史或证明旧进程停止 |
| 业务修订 / 事件游标 | 并发写条件与持久事件读取位置；不拿客户端时钟当全局因果顺序 |

Core 可以返回“已接纳操作”，之后再报告执行状态；每一步明确回执证明什么。连接断开、请求超时和取消等待不等于业务取消。Codex 的 typed request 和初始化机制不提供 Reed 所需的持久幂等保证，须继续采用 Orca 参考中的操作记录与恢复规则。

### 4.4 能力协商与双向交互

握手核验 Core 身份、profile、协议范围、服务代际和客户端能力；宿主名和能力声明不能替代认证。业务读写、原生会话控制、窗口导航及权限/输入呈现分别声明，不能只用“支持 Reed”布尔值表示。

后续需要用户输入或执行权限交互时，可学习 Codex 的服务端请求机制，但 Reed 的交互记录必须绑定操作、准确执行目标、有效期和实际授权主体。多个在线客户端同时收到展示，不代表都能批准；一次决定按修订/身份接纳，其他客户端收到已处理状态。界面重建不得重新批准旧交互，客户端离线也不自动授权。

上述多客户端展示仅针对 Core 有权管理且能可靠关联的交互，不将宿主原生审批复制为任意壳都可处理的通用弹窗。原生协议的回复可能绑定原连接和请求实例；执行器应持有准确回复路由，页面只能提交有限的用户决定。断线或回复失败时先核对原交互，不能换一个连接拿旧请求 ID 重发或假定已批准；同一用户决定也不自动授予另一次执行。

普通通知允许按客户端订阅范围裁剪；原生权限交互、持久操作结果和验收决定不能作为可任意丢弃的装饰事件。模型/Agent 文本中的“通过”不构成对应授权或验收。

## 5. 客户端与 Core 的边界

### 5.1 共享客户端承担什么

集中实现认证握手、协议/能力检查、传输请求关联、分层错误、订阅注销、事件游标、有限重连和 Core 发现结果解释。业务动作由客户端显式提交固定目标，不根据异步回调时的当前选中任务、cwd 或焦点重写目标。

错误至少区分连接/超时、协议解码、服务业务拒绝、并发修订冲突、效果未知及能力不支持。客户端不能按“出错即重试”统一处理；写入只有在应用规则允许时重传原持久请求，未知结果进入核查。

Core 不可达时先按受控启动入口发现/启动，或显示显式停止、维护、版本不兼容和故障。Reed 不采纳 Codex 的内嵌回退：Tauri、插件和 MCP 薄代理不得自行启动业务内核或新库来“继续可用”。进程内服务仅可作为明确隔离的测试装配，不改变生产单写入者拓扑。

### 5.2 客户端不承担什么

- 不直写 SQLite、恢复旧备份或执行 schema 迁移。
- 不在 UI 内实现阶段验收、云效仲裁、写入重试和资源占用释放。
- 不调用应用内部管理器或复制领域状态机，以规避某端缺失的公开能力。
- 不凭页面已隐藏/连接已断开推断 Agent 结束，不因退出 Tauri 停止 Core。
- 不因原生会话可导航就获得发送、取消和终态上报权限。

Tauri 与四端可以使用不同原生呈现组件；共享的是领域语义、投影和应用契约，不要求每端装同一 UI 容器。HostAdapter 的可信执行上下文负责原生动作，普通页面只持有有限能力。原四端能力验证缺口不因 Codex 源码存在接口而消失。

### 5.3 事件、响应与背压

Codex 针对 unread notifications 可能阻塞响应的问题，将部分客户端事件缓冲改成无界；这是其具体取舍，不能转述为低内存保证。Reed 应将控制响应/必要交互与高频日志的服务能力分开，定义字节与条目双重预算，避免某个慢页面拖住整个请求处理。

任务列表和历史通过快照/分页恢复，事件只提示增量。收到事件缺口、过期游标或服务换代时重取权威投影，不能仅靠前端回放猜状态。应设计无丢更新窗口的“快照修订 + 从该位置订阅/补读”流程；不是先随意读快照、再从当前时刻监听。

队列超限后合并可替代的显示更新，或中断该订阅并明确要求重取。持久操作结果和业务事件已在数据库提交，断开某个投影订阅不删除事实；权限请求等不可安全重建的交互须返回明确失败/待处理，不能悄悄丢掉。所有层分别设上限，不能用有界底层掩盖无界客户端缓存。

## 6. 生命周期：将原有规则变成组件契约

### 6.1 管理命令与业务运行分开

借鉴 daemon 的命令串行、版本报告和就绪探测，将运行管理职责明确给稳定安装/管理入口；不将独立 daemon crate 等同于必须新增一个常驻 supervisor。Core 的业务准入、运行锁和维护状态继续按原设计与 Orca 参考执行，安装器/控制锁不代替活写入者的互斥。

就绪判定包含认证、profile/schema、全局恢复屏障和可用用例，不止于 socket 存在或进程存活。Codex 的 probe 可作为“主动验证服务”的参考，Reed 需要自己的业务就绪契约。

原设计的按需启动、60 秒空闲后退出、用户显式停止、维护升级及无 Tauri 路径不变。不能继承 Codex daemon 自动更新/限时强停策略来替代 Reed 对活动执行、未知外部效果和数据迁移的保护。

### 6.2 准入 Permit 与活动执行分开

可学习 TurnAdmission：接纳和关闭使用同一短临界区，已接纳的准备/提交工作持有 Permit，正常完成或错误路径释放；进入 drain 后拒绝新接纳。等待外部工作时不持有该短锁，保持状态变更的边界清晰。

Permit 只证明准备/提交尚在应用流程内，不证明 Agent、CLI 或远端副作用已停止。进入 drain 要同时核对准入计数、受管理执行、工具进程、同步写入及落盘；不能只看到 Permit 归零就释放资源占用或数据库写入权。

Rust 的 Drop 或 TS 的受控 finally 可以辅助本地资源释放，但异步停止、文件刷盘和外部结果核查必须有显式完成路径。客户端取消等待只作用于该等待；真正取消执行是绑定准确目标的独立应用动作。

### 6.3 重启与迟到结果

客户端换连接/服务换代后重新核对绑定、协议与游标；业务操作从持久记录恢复。旧结果只进入原操作核查，不覆盖新 Task 轮次、执行绑定或云效期望。进程内 channel 被丢弃不代表外部工作停止，操作也不能只保存在 Promise、Tokio task 或连接 Map 中。

Codex ThreadStore 的 writer 所有权可作为执行日志管理参考；Reed 的本地 Task 身份、原生会话所有者、工作区写入占用与 Core 写库权分别管理。共享目录或使用相同配置不能代替对运行实例的准确发现与控制授权。

## 7. 存储：保留 SQLite 业务权威

### 7.1 明确借鉴哪一层

Codex 的 ThreadStore 提供 create/resume/append/flush/shutdown/read/list 等显式契约，且会话历史的 JSONL 与 SQLite 查询投影有明确先后关系。这有助于理解持久化边界，但不是要求 Reed 使用同一个大接口或相同存储布局。

Reed 保持一个业务权威：SQLite 中的 Task、范围/阶段、操作、验收、关系与同步意图事务。外部 Agent 的历史仍属于其来源；Reed 保存准确引用及按权限读取的必要证据，不复制全部聊天来重建另一套原生会话数据库。

| 数据类别 | 权威与恢复原则 |
| --- | --- |
| 任务、验收、操作、同步意图与业务事件 | Core 的 SQLite 事务；结果和相关业务事件按既定用例原子提交 |
| 文档/报告及其他文件产物 | 明确内容版本、哈希、索引及落盘流程；已登记不等于文件永远可用 |
| Agent 原生历史 | 准确来源引用及授权读取；缺失、不可访问和失联分别表达 |
| 日志、搜索、统计与可重建视图 | 衍生数据；允许延迟，不能领先于已提交业务事实 |
| 客户端缓存 | 可丢弃投影；不负责恢复验收或同步队列 |

不将 JSONL、SQLite 和前端 store 同时设成可各自修改的业务权威，也不为借鉴日志/投影模式引入完整事件溯源。导出/诊断 JSONL 可以是衍生制品，失败不反转已提交业务事务。

### 7.2 存储端口与事务边界

应用层依赖窄的存储/事务端口，按用例完成必要原子操作；接口表达并发修订、唯一性、读取范围和持久结果，不暴露 SQLite connection 或依赖“通用 CRUD”猜测业务原子性。不为每个表强制建一个仓储，也不提供随处向下转型拿具体数据库的通道。

客户端不调用 flush/shutdown 等内部 writer 方法来决定业务完成。Core 统一管理写入者及最终刷盘，外部 IO 在短数据库事务之外执行；结果未知通过持久调用记录恢复，而不是拉长事务等待网络。

文件产物沿用原方案的临时写入、校验、原子落位及索引登记；恢复区分未登记文件和内容缺失，缺文件不展示为有效证据。一致性备份、旧版本只读/拒写、恢复前隔离与未知效果保留继续引用原方案，不从 Codex 的会话修复机制推导任意业务库都可自动重建。

### 7.3 分页、物化与有界处理

游标绑定 profile、查询对象、过滤/排序范围与稳定位置，并带必要版本；换任务、换 Connector 过滤或改变排序时拒绝复用不匹配游标。游标不是访问凭据，每次读取仍检查权限。跨来源列表先明确稳定排序和去重，不能直接拼接各来源的游标。

大历史与日志采用固定上限的 keyset/游标分页，读取 pageSize + 1 判断后续；排序要有稳定 tie-breaker。页大小、单记录、解码后大小和输出大小都需有限制，避免“批次有界但单条巨大”。持续变化的数据若不提供一致快照，需说明分页语义并处理去重，不能声称永不漏项。

投影/索引分批重建，保存可恢复检查点；先接收/准备有界批次再进入短写事务，避免边等源数据边持有 SQLite 写事务。重建失败保留权威业务记录及原检查点，不能通过回放业务动作再次启动 Agent、回写云效或重做验收。

## 8. 工程机制与扩展

### 8.1 依赖规则成为门禁

借鉴界面依赖守卫，将原设计的边界列为后续可执行检查：共享 UI 不导入 Tauri/宿主 SDK，客户端不依赖数据库驱动，领域不依赖云效字段或传输，插件不复制阶段判定，生成契约与固定输入一致。

Codex 的源码字符串守卫是一个具体例子，不能认为足以阻止重命名、转导出或动态导入绕过。Reed 可按工具能力使用包导出约束、依赖图/静态规则和组合测试；既检查直接 import，也检查公开门面是否泄漏内部对象。先覆盖真实边界，不建设泛化架构规则平台。

### 8.2 内部扩展、宿主插件与 MCP 分开

可用类型化注册将来源、宿主与执行实现注入 Core；启动装配完成后，执行期使用固定能力快照，变化按明确版本/重载流程生效。此处不要求增加任意代码 hook、热加载或第三方 native 插件机制。

Codex 的内部 contributor registry、面向用户安装的插件和 MCP 工具接入是不同层次。Reed 首版继续维护 ProviderConnector、HostAdapter、AgentExecutor 三种边界；协议生成或统一注册表不能把它们合成拥有全部权限的插件对象。

### 8.3 可解释配置与版本

配置可保留原始来源、生效值、覆盖原因及修订，供界面解释“这次为何使用此工作流/映射/执行选项”。业务输入在 StageRun/Attempt/SyncIntent 接纳时固定，之后更改默认配置不静默改变已有执行。

无需照搬 Codex 的全部系统/企业/MDM 配置层。Reed 先按实际需要明确 profile、项目、模板/映射和本次明确选择的责任；权限限制与必需验收条件不是普通偏好，不能通过高优先级自由配置覆盖。凭据材料仍在独立安全存储中，不成为可展示的配置来源正文。

统一版本和依赖约束、格式/lint、协议生成检查、分层测试及发行输入核验值得借鉴；Codex 的 Rust release 参数只是它的构建选择，不能作为 Reed 性能结果或最优编译参数。Core、客户端、UI、Tauri 和适配插件版本仍分别记录并验收。
