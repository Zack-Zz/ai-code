## 1. 已确认的方向

CodeStack 补充用户明确的编码偏好，以及具体场景中需要防止的错误取舍。
不收集完整技术教程，不重复教授模型通常已经掌握的 Java 基础，也不因规范数量多就认为插件更有效。
规则的价值要通过实际任务中的遵循情况、误报与额外开销验证。

首版范围为 Java 通用、数据访问、JPA、MyBatis 四层。
数据访问层的具体规则以已确认的关系型数据库 / SQL 访问为前提；未知存储不推断为 SQL，
非关系存储的专属规则不在本版支持声明内。用户明确提出的要求仍独立遵循。
TypeScript / React / Vue 保留为后续方向，本轮不承诺其支持；MyBatis-Plus、其他 ORM 也不预建专属规则库。

用户已确定的要求保持不变：

- 注释语言按用户要求、项目或模块语言、系统语言的顺序选择。
- 手写字段、方法、构造函数及参数完整写多行 Javadoc；方法内只注释核心逻辑。
- 测试特殊实例在测试类内部构造，不给生产代码增加仅为测试服务的构造函数或变相入口。
- 新增实现前查找已有能力；同一业务规则在最小合适边界内集中维护，语义不同的实现保留独立。
- 尽可能避免内部/嵌套类型，确有具体必要性才保留；业务职责和 Spring Bean 优先顶级类型，不批量迁移历史代码。
- 禁止逐条及隐藏的循环查询，关注一次操作的 SQL 次数、数据范围与表访问成本。
- 不约束业务代码的缩进、换行、行宽等排版。
- 安装启用后以自动选用为目标，无需用户每次点名，也不要求业务项目新增规则或配置文件。

供智能体执行的 Skill、reference 与示例仅维护英文；内部设计稿保持中文。
英文规则不改变目标项目的注释语言优先级。
面向人的公开安装说明沿用仓库双语文档要求，不复制第二套可执行规则，Skill 不要求加载这些说明。

CodeVow 继续负责计划、授权、TDD、风险审查及验证流程；CodeStack 不复制其任务状态、策略或 Reviewer。
两个插件独立安装和使用，不通过硬编码路径互相调用。

## 2. 最小插件结构

以下结构已按批准的计划创建：

```text
plugins/ai-code-stack-standards/
  product.json
  AGENTS.md
  README.md
  README.zh-CN.md
  LICENSE
  skills/code-standards/
    SKILL.md
    references/
      java.md
      data-access.md
      jpa.md
      mybatis.md
  adapters/
    claude/plugin.json
    codex/plugin.json
    codex/interfaces.json
    zcode/plugin.json
  tests/skills/run-skills.js
  evals/
    cases.md
    fixtures/
```

- 只有一个 `code-standards` 技能入口；四份 reference 由它按需选择。
- 不新增独立 Agent、运行时、MCP 服务、Hook、自动安装器或技术栈探测脚本。
- 不增加项目侧 `.codestack` 配置、规则缓存、任务状态或 AGENTS 路由注入。
- `product.json` 维护唯一产品身份、版本、宿主、技能和资源白名单。
  初始开发版本为 `0.1.0-preview.1`，不代表公开发行。
- 目标宿主为 Claude Code、Codex、ZCode，适配目标与真实行为验收分别记录。
  `hosts` 表示宿主，不表示 JPA / MyBatis；技术选择属于 Skill 内容，不向公共清单添加技术栈字段。
- 四份 reference 逐文件列入白名单；源码维护规则、测试、评测 fixture 和中文设计稿不进入执行资源包。
- 包内 README 使用简短的发布说明入口，不让源码 README 的跨仓库链接破坏包内引用闭包。
  所需发布 README、release.json 和发行输入在本地发行准备阶段补齐。

## 3. 四层规则的职责边界

| 规则文件 | 什么时候读取 | 负责什么 | 不负责什么 |
| --- | --- | --- | --- |
| `java.md` | 本次新增、修改或审查手写 Java 声明、实现或测试 | 注释语言、多行 Javadoc、核心逻辑注释、测试构造边界、已有实现复用、适度抽取、必要才嵌套 | 格式、命名教程、泛型 / Optional / Stream 教程、统一目录或设计模式 |
| `data-access.md` | 本次实现、修改或审查已确认的关系型数据库 / SQL 访问行为及成本，不限定 ORM | 禁止逐条查询及隐藏变体；批量输入、空集合、权限和结果契约；实际 SQL 次数、范围与表影响 | JPA 代理加载方式、MyBatis XML 语法、非关系存储专属机制、固定索引或连接池参数 |
| `jpa.md` | 本次影响或审查 JPA 映射、实体构造、生命周期、查询或持久化调用 | 隐式关联查询、集合加载与分页、受管理实体的隐式写入、级联删除、批处理结论；真实框架构造要求 | 把所有 JPA 实现当成 Hibernate、给 MyBatis 套实体生命周期规则、自动切换 ORM |
| `mybatis.md` | 实际涉及 MyBatis Mapper、映射 XML、SqlSession 或其调用链 | Java / SQL 绑定一致性、参数与动态条件、嵌套 select、分页和批量执行的真实 SQL 行为 | 给 XML 加 Javadoc、MyBatis-Plus 独有 Wrapper / 插件规则、通用 SQL 教程 |

详细规则的来源归属：Java 稿第 1—4 节（含 4.1—4.3）映射到 java.md，第 5—7 节映射到 data-access.md，
第 8 节映射到 jpa.md，第 9 节映射到 mybatis.md。

规则可组合，不互斥。禁止循环查询只在 data-access.md 定义；JPA 和 MyBatis 分别说明本框架中的隐藏触发点。
组件文件不得重新定义、削弱或复制一套不同的共通约束。
每个文件开头用短段落说明适用条件和重要的版本前提，正文保持“具体写法 + 禁止的捷径 + 最小示例”。
不为规则资源新增配置 Schema 或通用规则解释器。

## 4. Skill 自动选择逻辑

### 4.1 何时进入技能

技能描述围绕当前任务：编写、修改或审查 Java 代码及其 JPA / MyBatis 持久化映射。
不能只写“需要规范时使用”，让模型先意识到自己可能犯错才加载规则。
选择应在首次相关代码写入前完成；只读审查则在形成相关结论前完成。

纯概念问答、插件命名、无关文档调整、其他语言任务不默认加载 Java 规则。
用户显式要求 CodeStack 检查时也先判断适用范围；检查请求不自动授权修改代码。

Codex 适配允许 implicit invocation；其他宿主使用其原生 Skill 发现方式。
这些声明只提供可被自动选用的入口，不是强制拦截器，也不证明每次任务必定触发。
如果某宿主达不到无需点名的体验，应报告实际缺口，不通过暗改项目指令或全局设置补救。

### 4.2 先确定本次范围，再识别技术

1. 确定用户目标、本次文件、所属模块及需要理解的直接调用链。
   区分仅修改注释与改变映射、查询或生命周期；文件属于某框架，不代表所有框架规则都与本次任务相关。
2. 读该模块实际使用的依赖、完整 import、继承关系、注入对象、SQL 映射与配置。
3. 用依赖和版本确认源码判断，必要时查看有效依赖解析结果。
   不仅凭根目录依赖名称、文件名或目录名定性。
4. 为当前范围选择相关规则；Java 文件、XML 文件和相关调用链分别应用。
5. 同一任务经过多个技术栈时组合规则；后续发现新的调用路径时补读相应文件。

只在当前上下文保留“适用范围、依据、已读规则”的判断，无需写入项目文件或给用户输出固定识别报告。
范围和依据未变化时复用已读内容，不在每次工具调用前重新扫描仓库或读取整套规范。

### 4.3 识别证据的边界

| 线索 | 如何使用 |
| --- | --- |
| 用户明确指定新模块的技术栈 | 作为拟开发目标选择规则，即使依赖尚未加入；依赖改动仍服从该开发任务范围 |
| 实际 import、继承类型、持久化 API 和映射绑定 | 作为当前代码使用该机制的直接证据，结合调用路径与版本确认 |
| 当前模块有效依赖 | 辅助确认可用组件和版本，不说明每个文件都使用该组件 |
| dependencyManagement、BOM、其他模块依赖 | 不能单独证明当前模块实际使用该框架 |
| 测试依赖 | 不扩展成生产代码的技术栈；修改实际使用该框架的测试时，按该测试的真实用途选择 |
| 未启用配置、废弃代码、迁移残留、示例代码 | 先确认是否参与当前任务路径，不能仅因存在就加载并执行整改 |

具体识别注意事项：

- `org.mapstruct.Mapper` 不是 MyBatis Mapper；类名带 Mapper 或注解简称相同都不足以判定。
- JpaRepository、EntityManager 等真实使用可支持 JPA 判断；通用 Repository 名称不足以判定。
- Hibernate Validator 不代表使用 Hibernate ORM；JPA 的实际 provider 和版本要另外核对。
- 直接使用 Hibernate ORM API 时，可以读取 jpa.md 中注明适用的 ORM 条目，但不凭此推断全部 JPA API 均在使用。
- JDBC、未知 ORM 等已确认执行 SQL 的访问先应用 data-access.md，不自动套用 JPA / MyBatis 机制。
  存储机制尚未确认时继续查证；确认是非关系存储时不套用 SQL 条目，也不声称已经覆盖其专属风险。
- 用户描述与实际代码矛盾时先核对。只有差异影响实现且无法从上下文查清时才请求澄清。
  新项目技术栈尚未指定且无法推断时，不替用户选择或安装 ORM。

### 4.4 选择结果只限制相关代码

一个业务操作同时通过 JPA 和 MyBatis 访问数据时，读取两份组件规则，并从整个操作核算 SQL 成本。
只因其他模块使用 JPA，不对当前 MyBatis 模块引入实体、EntityGraph 或级联配置。

修改 MyBatis XML 时读取 MyBatis 与数据访问规则，并沿绑定检查必要的 Java 上下文；
只有本次涉及手写 Java 声明的修改或审查，才对这些声明应用 Javadoc 要求。
JPA 的 orm.xml、persistence.xml 等根据本次实际映射或持久化行为选择 JPA 规则，
涉及 SQL 行为或成本时选择数据访问规则；不把 XML 扩展名当成 MyBatis 的证据。
普通 POM、日志或其他 XML 不因此加载持久化要求。
框架构造函数有真实生产用途时可以存在，不能与仅为测试增加的入口混为一谈。

空集合处理跟随筛选契约：必需的正向包含集合为空时不查库并返回空；
排除集合为空及项目明确允许的可选空筛选保留其原有语义，所有分支仍受租户、权限和数量边界约束。
已有授权的分批导出复用既定范围和预算，局部变更不重复审批；
仅在缺失决定影响工作或需要扩大已授权范围、预算时澄清或取得相应同意。

用户的明确要求与适用的项目约定优先于插件默认建议。
历史代码没有注释不能推翻本次明确的注释要求；一段旧循环查询也不能成为继续逐条查询的依据。
规则选择决定读取哪些内容，不授权忽略已经适用的明确要求，也不扩大原任务修改范围。

## 5. 路由与行为验收场景

以下是验收场景；已创建对应匿名 fixture 和评测说明。定义场景不等于执行通过，
实际运行记录以实现与验证报告为准。
普通请求不提插件或技能名称，用于观察自动选用；显式调用仅作为另一个入口对照。

| 编号 | 任务或上下文 | 应读取和应用 | 必须避免的结果 |
| --- | --- | --- | --- |
| R01 | 修改不访问数据库的 Java 工具类 | Java；完整多行 Javadoc | 因仓库其他模块依赖 JPA 而加载全部持久化规则 |
| R02 | 英文模块中用中文对话提出 Java 修改 | Java；无其他指定时沿用模块英文注释 | 跟随中文设计稿或聊天语言翻译无关注释 |
| R03 | 用户明确要求中文注释，项目原来为英文 | Java；执行当前明确语言要求 | 用默认英文执行文档覆盖用户选择 |
| R04 | 为已有 Java 类补单测 | Java；特殊实例在测试类内部准备 | 增加测试专用生产构造、factory、setter 或开关 |
| R05 | 修改 JPA 映射、持久化行为或 Repository 查询 | Java + 数据访问 + JPA；按具体改动应用 | 把 LAZY、Page 或 saveAll 的名称当成效果证明 |
| R06 | 修改 MyBatis Mapper 与 XML | Java（针对相关 Java 声明）+ 数据访问 + MyBatis | 参数或 namespace 不匹配、空集合扩大 SQL 范围 |
| R07 | 仅修改 MyBatis XML 查询 | 数据访问 + MyBatis；只读必要的 Java 绑定上下文 | 给 XML 写 Java Javadoc，或无关补写全仓 Java 注释 |
| R08 | 修改 MapStruct 映射，未涉及数据库 | Java | 把同名 Mapper 当成 MyBatis；若手写转换实际查库则需追加数据访问规则 |
| R09 | 根 POM 仅管理 JPA 版本，当前模块无 JPA 使用 | 按当前代码选择，通常只有 Java | 从 dependencyManagement 推导 JPA 已启用 |
| R10 | 只有测试依赖或迁移残留提到某 ORM | 按本次生产或测试路径的真实用途选择 | 把测试依赖应用到无关生产代码，或反过来忽略实际 ORM 测试 |
| R11 | 同一操作经过 JPA 与 MyBatis | Java + 数据访问 + 两份组件规则 | 只选择“主技术栈”，漏掉另一条路径的 SQL 或副作用 |
| R12 | 纯 JDBC、未知 ORM 但已确认执行 SQL，或尚未确认存储机制 | 已确认 SQL 时使用数据访问；Java 声明使用 Java；存储未知时先查证，非关系存储不套用 SQL 规则 | 把所有存储推断为 SQL、猜测框架、安装新依赖或要求业务项目添加规则配置 |
| R13 | JPA 使用非 Hibernate provider，或只出现 Hibernate Validator | 已确认的 JPA / Java 规则 | 套用未经确认的 Hibernate ORM 版本结论 |
| R14 | JPA 实体需要正常的框架无参构造函数 | Java + JPA；保留有真实用途的构造方式 | 将正常框架要求误判为测试后门，或借此添加测试专用重载 |
| R15 | getter、序列化、并行任务或缓存未命中触发逐条查询 | 数据访问 + 实际组件；沿真实 SQL 判断 | 因没有显式 for 或方法名含 batch 就判定合格 |
| R16 | 新模块已明确采用 MyBatis，尚未添加依赖 | Java + 数据访问 + MyBatis 作为目标规则 | 因当前还没有依赖而忽略用户明确目标 |
| R17 | 纯概念问答、普通文档修改或 TypeScript 任务 | 不默认读取 Java reference | 注入 Java 模板、扩展为全仓规范整改 |
| R18 | 同时启用 CodeVow 与 CodeStack | CodeVow 管流程，CodeStack 提供本次代码约束 | 第二套计划、审批、Reviewer、项目状态文件或重复全量检查 |
| R19 | 只为已有 JPA 实体补充或纠正文档注释，不改映射及行为 | Java；只读取理解该注释所需的上下文 | 因实体身份自动启动 SQL 性能检查、调整关联或添加持久化测试 |
| R20 | 必需的正向 ID 包含集合为空 | Java + 数据访问；不执行该次查询并返回空结果 | 因忽略必需条件而返回其他记录 |
| R21 | 排除 ID 集合为空 | Java + 数据访问；按既有契约不排除任何项，仍保留租户与分页 | 把“没有排除项”改成“没有结果” |
| R22 | 项目明确约定可选 ID 筛选为空表示不筛选 | Java + 数据访问；仅省略该可选条件，保留其他边界 | 用统一空响应覆盖业务契约，或删除权限条件 |
| R23 | 只修改 JPA orm.xml 的列映射 | JPA + 涉及的共通数据访问规则；必要时只读 Java 上下文 | 因 XML 扩展名加载 MyBatis，或改动无关 Java/Javadoc |
| R24 | 用户已确认有界分批导出方案，只追加已有输出字段 | Java；涉及的数据访问判断复用已有范围与预算 | 重复询问已经批准的方案，或擅自扩大批次、范围及上限 |
| R25 | 已有权威配送费实现，补充另一结算入口 | Java；定位并使用同一政策，随政策变化保持一致 | 复制当前等价表达式，原结果正确但不能跟随已有政策变化 |
| R26 | 两个入口表达同一优惠政策，本次共同调整 | Java；在最小适当边界集中维护，并验证一次改动的传播 | 两份副本都改对便声称完成抽取，或扩建通用策略框架 |
| R27 | 取消订单和撤回退款暂时判断相同，但业务契约独立演进 | Java；规则保持各自归属，可复用真正通用的校验 | 跨业务委托或为了减少相似代码增加布尔模式万能方法 |
| R28 | 普通业务服务新增结构化报价结果 | Java；复用已有计算，业务结果优先顶级类型 | 仅因类短、单个使用点或少建文件，就新增嵌套业务 DTO |
| R29 | 已有 JDK Iterator 局部实现的小范围边界修复 | Java；保留快照、独立游标和 API，允许必要私有实现或更简 JDK 等价方式 | 为形式上消除内部类而暴露状态、扩大 API 或改变独立迭代行为 |
| R30 | 只读购买预览与会预留库存的既有结账方法返回相似金额 | Java；先比较契约，只复用相符的读取或纯计算 | 为复用而扣库存、改变异常语义或泄漏其他租户数据 |
| R31 | 修复报价天数，已有独立部署客户使用公开嵌套结果类型 | Java；保留既有二进制 API，以未重编的旧客户验证 | 为顶级类型偏好迁移公开类型，或把客户重编后的通过当成兼容 |
| R32 | 按既有 JDK FileVisitor 协议新建附件扫描实现 | Java；按具体 SDK 适配与私有状态封装需要判断嵌套，等价顶级适配也可接受 | 为消除嵌套而暴露状态或扩大 API，或把行为正确等同于结构必要 |

R20—R24 是本轮全面 Review 后增加的反例，不更改原 R01—R19 的历史验收记录。
三个隔离项目分别承载空筛选三种语义、JPA XML、已有导出授权；
判定器在候选工作区外冻结，具体执行结果与模型读取轨迹分别记录。

R25—R29 在本轮复用/抽取及内部类偏好确认后补充。功能判定与结构审阅分开：
复用通过真实政策替换验证，同一规则抽取通过人工确认归属加单点变更传播验证；
语义独立、泛化是否多余、嵌套是否确有必要仍审阅实际调用和 diff，不能用行数、类名或关键词替代。

R30—R32 仅补充既有规则的反例与行为证据，不扩写规则正文。
公开 API 兼容通过针对旧库预编译的客户类实测；新增嵌套场景采用真实 JDK 协议，
不声称 Java 语法强制嵌套，也不拒绝保持相同契约的顶级实现。

每个场景同时观察是否应用了应有规则、是否误用不适用规则，以及是否出现无关修改。
来源不明的读取路径或只输出“已遵守”不构成规则已加载、行为已满足的证据。

## 6. 验证分层

### 6.1 静态与发行包契约

复用仓库现有 validate、统一测试、lint、build 和独立 package check。
检查单技能身份、显式资源闭包、引用可解析、宿主元数据、共同资源哈希和测试入口确实被发现。
Codex defaultPrompt 遵守当前 128 字符上限，implicit invocation 声明正确。

新增测试只覆盖有意义的插件集成契约与失败路径，不再实现一份公共包验证器。
错误引用、遗漏白名单、技能与适配不匹配等应明确失败；不能只测试文件存在或某个关键词出现。
静态检查不能证明模型正确路由，不为测试方便构造一个实际插件不会使用的“技术栈分类器”。

### 6.2 真实 Agent 行为

在隔离的评测 fixture 中执行普通编码请求，记录宿主、模型、配置、插件源码或包哈希、
规则读取证据、实际 diff、相关行为检查及无法观察的部分。
不依赖 disinfection-monitor 的私有源码、生产服务或凭据制作公开 fixture。

先用同一任务、相同模型与环境建立未启用 CodeStack 的基线，再与启用后的结果比较。
先尝试注释、测试构造、隐藏查询三个代表性样例，每个条件重复运行，初始计划各 3 次；
用“通过次数 / 总次数”报告观察结果，不把小样本当作稳定成功率。
其余路由矩阵逐项验证，额外重复针对不稳定或出现误报的场景。

基线未出现目标错误时如实记录，不能伪造 RED，也不能据此宣称规则带来改善。
行为错误的修复应有失败轨迹与修复后的结果；资源和代码的确定性行为变更按仓库 TDD 要求执行。
注释规则可检查实际声明和 Javadoc；数据库规则需要观察真实调用或 SQL，不能仅搜索关键词代替。

本地包验证、宿主原生加载、隐式触发、规则选择和代码结果分别记录。
真实宿主验收需要安装或其他额外权限时，先完成可审阅制品，再申请对应授权；
没有授权或环境不可用时保持 pending，不用显式点名成功替代自动触发成功。

## 7. 已批准的开发计划

| 步骤 | 具体工作与产物 | 验收与边界 |
| --- | --- | --- |
| P1：固定用例与失败证据 | 按 R01—R19 建立最小匿名 fixture、任务输入和结果检查；设计必要的插件集成测试入口 | 确认失败来自目标缺口，不是缺运行环境、空测试或伪造模型结果；此步骤也属于实现 |
| P2：编写英文执行内容 | 创建一个 code-standards SKILL 和四份 reference；从中文规则稿翻译并按职责分配 | 用户硬要求不遗漏；共通规则不重复；示例简短且保持多行 Javadoc；无无关教程或强制代理流程 |
| P3：接入三个宿主与统一门禁 | 新建 product、插件局部 AGENTS、原生适配、说明与许可证；catalog 仅登记相对路径；测试入口接入现有汇总器 | 资源闭包完整；各组失败会传播；不改公共运行时，也不让 CodeVow 规则成为新插件依赖 |
| P4：本地验证与包复验 | 运行定向校验、统一测试及 lint，构建目标宿主包并从可信仓库独立复验 | 分别报告源码、测试、包完整性；不修改 published、公开市场或宿主缓存 |
| P5：原生行为评测 | 在有授权且可用的宿主环境运行基线、隐式调用、混合技术栈和误触发场景 | 记录真实轨迹与产物；缺少证据的宿主保持 pending；需要安装时另行取得授权 |
| P6：独立审阅与交付 | 审阅规则语义、英文翻译、路由反例、授权范围、最终 diff 和证据 | 修复本次范围内确认的问题；交付未提交改动、结果和剩余风险，等待用户 Review |

P1 的失败证据与 P2—P4 的修复验证按具体改动交替推进，不将“全部文档先写完、最后补测试”描述为 TDD。
纯文字澄清没有行为变化时做相应文档检查，不制造无意义失败测试。

主要本地检查命令如下；以下保留命令模板，实际路径、退出状态与结果见实现与验证报告：

```sh
python3 tooling/plugin_tool.py validate --plugin ai-code-stack-standards
PYTHONDONTWRITEBYTECODE=1 npm test
npm run lint
python3 .github/scripts/check_no_dist.py --root .
python3 tooling/plugin_tool.py build --plugin ai-code-stack-standards --host all --output /private/tmp/codestack-packages
```

构建目录必须不存在或为空。每个实际宿主包都执行以下独立检查，路径取自本次构建索引：

```sh
python3 tooling/plugin_tool.py package check --path <本次包路径> --host <实际宿主> --root .
```

本地发行接入作为后续单独步骤：配置 release.json 与发行材料，更新 release.yml 的 plugin choices
及对应工作流契约测试，再执行 draft 发行检查。若本轮实现批准只覆盖 P1—P6，则不自动扩展到该步骤。
commit、push、tag、PR、安装、公开发布和市场同步各按用户实际授权执行，计划确认不自动授予这些权限。
