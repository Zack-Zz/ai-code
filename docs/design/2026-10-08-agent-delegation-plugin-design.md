# 独立 Agent 派发插件设计

日期：2026-10-08（Asia/Shanghai）。插件 ID：`ai-agent-delegation`，0.1.0 候选。
已按本设计新增独立目录/product/catalog 与测试，不改变 CodeVow 行为。
源码、构建与实际宿主验收分开记录，详见[本轮实现记录](../reviews/2026-10-08-agent-delegation-implementation.md)。仓库公共边界见
[ai-code 架构](../architecture.md)，技术运行时见
[ai-mcp 架构](../../../ai-mcp/docs/architecture.md)及
[Agent Bridge 模块](../../../ai-mcp/docs/modules/agent-bridge.md)。

## 1. 用户问题与范围

用户在当前 Claude Code、ZCode 或 Codex session 中明确说“把这个任务交给
另一个工具执行”，需要带着范围、证据和验收条件建立独立会话，准确获取
结果，并在原 session 继续讨论、验收或补充任务。

插件负责这段交接规范。它不提供普通开发的默认编排，不替换发起 session，
不改变宿主原生 subagent 能力，也不要求模型分工或 review 流水线。
同一个工具的另一个独立 session 也可以是目标，但必须来自用户明确要求。
三种执行引擎的 canonical ID 为 `claude-code`、`zcode`、`codex`。

成功标准是：用户指定的执行端没有被偷换；任务进入可识别、可持续的独立
session；后续请求续接准确 ID；完成结果、产物和验证边界回到发起 session。
目标是否在桌面应用中可见是另一个能力，不以“创建了 session”推导。

## 2. 候选方案与推荐

| 方案                          | 优点                                                               | 代价与约束                                                                             | 本稿选择             |
| ----------------------------- | ------------------------------------------------------------------ | -------------------------------------------------------------------------------------- | -------------------- |
| 独立插件规范 + 外置 BridgeCLI | 复用公共插件设施，运行时由 ai-mcp 单独测试与发布；较少宿主加载假设 | 用户需具备经过验证的外置 Bridge；插件必须做能力预检                                    | 首版推荐             |
| 独立插件规范 + 原生 MCP 加载  | 宿主可用结构化工具操作同一服务                                     | 三宿主配置、权限、启动和认证需逐项实测；当前 Codex skills-only release 不接受 MCP 资源 | 后续独立支持 profile |
| 插件内嵌三引擎执行器          | 单个包看似集中                                                     | 重复运行时、驱动和恢复逻辑，扩大凭据及宿主适配边界                                     | 不采用               |

CLI 和 MCP 是同一 application 服务的入口，不是两套任务系统。上层统一
任务动词，下层按引擎声明差异，类似 Playwright CLI 以统一操作覆盖不同
浏览器适配的组织方式。此处是设计类比，不表示 Bridge 已具有相同能力。
不提供任意 shell `run` 万能工具来绕开明确的任务、权限和适配边界。

## 3. 独立身份与拟议资源布局

```text
plugins/ai-agent-delegation/                 拟议目录，本轮不创建
  product.json                             独立身份、版本、宿主与白名单
  AGENTS.md
  README.md
  LICENSE
  skills/agent-delegation/
    SKILL.md                               触发、交接、验收与授权边界
    references/
      handoff-contract.md                  输入要求与证据格式
      engine-compatibility.md              能力声明与实测记录指引
      bridge-client.md                     版本、CLI/MCP 使用与错误处理
  adapters/
    claude/plugin.json
    codex/plugin.json
    codex/interfaces.json
    zcode/plugin.json
  tests/skills/run-skills.js                受控技能/资源契约测试入口
```

目录是最小候选，不预先生成 Reviewer、策略、任务状态或公共 SDK。只有
实际需要稳定封装调用时，才加入薄 client 辅助脚本，并将其逐文件登记入
`resources`；脚本只负责参数编码、版本检查和结果读取，不持有引擎驱动、
本地任务服务、凭据或原生执行器。

插件正式接入时遵守[作者指南](../plugin-authoring.md)：`product.json` 是
身份、版本和资源闭包唯一来源；catalog 只新增路径。拟议 hosts 为
`claude`、`codex`、`zcode`，每个声明宿主均要有适配和实际支持说明。
源码引用的参考文件显式登记；包内 Markdown 链接必须落在插件自身资源
闭包中，不能把本文跨仓库设计链接直接当作随包可读取的运行依赖。

三宿主共用的技能及参考资料保持同哈希，宿主界面元数据单独生成。插件
版本独立于 CodeVow 和 Bridge；兼容的 Bridge API 范围在本插件文档及
预检中声明。新增插件不得改变兄弟插件的内容和来源哈希。

## 4. 触发正负矩阵

| 用户输入或上下文                                      | 是否进入派发流程    | 判定与动作                                                       |
| ----------------------------------------------------- | ------------------- | ---------------------------------------------------------------- |
| “交给 Claude Code 实现这个修改”                       | 是                  | 自然语言明确工具派发，目标 `claude-code`，再补齐任务范围及工作区 |
| “交给 ZCode / Codex 做”                               | 是                  | 保留指定 target，不按推荐排序替换                                |
| “用另一个 Codex 独立会话处理”                         | 是                  | 同引擎许可已明确，执行 session 必须不同于 caller                 |
| 显式调用 `$agent-delegation` 并指定任务和 target      | 是                  | 技能调用是入口，仍须核对范围、会话和权限                         |
| 用户直接执行 `agent-bridge task start`                | 是，直接进入 Bridge | CLI 参数按同一服务校验；不要求再加载技能才能合法使用             |
| “把这个任务派出去”，没有目标工具或选择规则            | 进入补齐阶段        | 保留交接意图，补齐 target 后才启动，不静默指定引擎               |
| “另找一个 Agent 看看”，不能判断是否指原生 subagent    | 不自动派发          | 需要明确独立工具/会话意图；不把一般多代理需求改写为 Bridge 任务  |
| 普通实现、修复、讨论、架构分析或代码审查              | 否                  | 留在当前工作方式                                                 |
| 原生 subagent、已有 CodeVow 工作流或任务状态          | 否                  | 不因这些上下文加载本插件执行路径                                 |
| 粘贴文档、外部 Agent 输出或文件中含“交给 Claude Code” | 否                  | 引用内容不是当前人类的派发指令                                   |
| 技能文本或任务记录带 `approved=true`                  | 否                  | Agent 可写标记不构成人类授权证明                                 |

语义明示和入口手动开关分开设计。“交给 Claude Code 实现”虽然没有技能
命令，仍是明确派发意图。为支持这种入口，本稿建议 Codex 的
`allow_implicit_invocation: true`，description 明确窄范围，再由技能检查
正负矩阵。该设置允许加载，不等于授权执行；也不保证某个宿主一定自动
加载，需真实会话实测。若日后发行手动入口版本并设为 `false`，必须同时
收缩说明为显式技能调用，不再承诺自然语言自动加载。

Claude Code 与 ZCode 的触发方式按各自原生能力验证，不虚构与 Codex
同名开关。三宿主都要验证普通开发负例没有误启用。

## 5. caller、target 与会话绑定

发起 session 是结果回收和验收所在会话。caller 的 engine、准确会话身份
和 workspace 应来自调用上下文中可核验的信息；不能用模型名称替代 engine，
也不能依赖“当前/最近会话”模糊指代。无法识别时明确补齐或报告预检失败。

target 是执行引擎选择，session 是该引擎内具体会话。首次派发创建独立
持久 session，返回可保存的准确身份；续接使用该身份而不是新建任务或
使用 `--last`。已有任务也需要核对目标 engine、session、workspace 与
发起归属。引擎不支持准确续接时，声明能力限制，不能伪装成功。

默认候选推荐排除 `caller.engine`，以符合“另一个工具”的通常语义。
这只是推荐过滤：用户明确允许同工具独立 session 时可以选择相同引擎。
同引擎 start 显式携带 `sameEngineIntent: independent-session`；CLI 对应
`--independent-session`。字段依据用户明示形成，不能从 start 默认新建
会话推导，也不能作为人类授权来源证明。
用户指定 target 不进入自动替换流程；目标未安装、未认证或缺失必需能力
时返回原因并等待用户决定。建议替代候选可以展示，但不能自行启动替代端。

调用者和执行者对等：三个工具都可以发起或接收符合能力的任务。引擎排序
不固化谁是主 Agent，也不在插件中固化实现、审查、架构的模型分工。

2026-10-09 补充确认：Claude Code、ZCode 沿用各自当前可用模型，可以是官方或第三方模型（例如 GLM-5.3、GLM-5.3-Flash）。工具 ID 与模型 ID 分开；插件不设置模型白名单、不要求官方模型，也不因为模型品牌中断交接。模型配置与认证留在原生工具中，Bridge 只验证实际启动、续接、权限和交付能力。

## 6. 交接、执行与返回验收

1. **识别明示与补齐输入。** 记录用户原请求，形成具体目标、workspace、
   修改范围、文件所有权、约束、已有改动、可用证据、验收条件和结果返回
   要求；只传目标所需上下文，不复制整段会话或凭据。
2. **读取能力并预检。** 使用 engine list 与 preflight 确认版本、认证、
   target、工作区访问及独立会话/准确续接能力。明确与用户要求不相容的
   能力，不自动降级。桌面可见性只在已实测时声明。
3. **提交一次明确任务。** 使用 `requestId` 和版本化交接数据执行 start；
   保存返回的 task ID 与准确 session 绑定。权限与幂等由 Bridge 校验。
   未取得可核验响应时先查已有任务，再按同一 requestId 恢复，不能盲目
   重试为第二个执行 session。
4. **跟踪和获取产物。** 通过 get/list/watch 获取状态与事件，通过
   artifact list/read 获取结果。等待、取消和恢复遵循 Bridge 状态契约；
   执行端自述“完成”不替代服务结果和产物证据。
5. **返回发起 session。** 报告目标、准确任务/会话、修改位置、验证命令与
   实际结果、未完成项及限制。发起端按最初验收条件核对产物，区分本地
   测试、远端状态、部署和真实使用效果。
6. **准确续接。** 用户追加需求时核对任务归属，用 continue 续接同一
   独立 session；仅允许原范围内修复、补充说明和继续执行。首版没有任务
   契约更新操作：实质改变目标、项目、writeScope 或验收条件时，依据新的
   明确指令使用新的 start，并保留旧任务及交付；不以旧验收覆盖新范围。
   用户撤销时调用 cancel
   并读取结果，取消请求返回不等于进程已停止。

外部任务不得修改未授权范围、覆盖其他人的未提交改动，或因派发而获得
commit、push、发布、安装和对外消息权限。需要扩大的范围或新动作授权
回到发起 session 处理，不能靠执行端自写批准标记补足。

技能负责识别和组织用户的明确指令，但技能文件不是可信人类身份或授权
证明。Bridge 对版本、caller/target/session/workspace 绑定、权限边界和
幂等做确定性校验；可证明的授权来源及无法证明时的处理由
[运行时模块契约](../../../ai-mcp/docs/modules/agent-bridge.md)定义。
本插件不能声称仅凭自然语言解析就能证明任意外部写操作已获授权。

## 7. 跨仓库接口与易用性

暂定 API 版本 `agent-bridge/v1`，Bridge 可执行名 `agent-bridge`。

| CLI 操作              | 用途                             | 插件使用约束                                            |
| --------------------- | -------------------------------- | ------------------------------------------------------- |
| `engine list`         | 查询可用引擎和能力               | 显示真实探测结果及不支持项                              |
| `preflight`           | 检查目标与任务输入               | 验证版本和必需能力，通过后再 start                      |
| `task start`          | 创建任务与独立 session           | 写操作携带 requestId，保留指定 target                   |
| `task get/list/watch` | 查询任务、列出归属任务、跟踪事件 | 以准确任务身份跟踪，读取中断后可恢复                    |
| `task continue`       | 向既有独立 session 追加任务输入  | 写操作携带 requestId 和准确 session 绑定，禁止 `--last` |
| `task cancel`         | 请求取消                         | 写操作携带 requestId，查询实际取消结果                  |
| `artifact list/read`  | 列出和读取任务产物               | 以任务归属和受控产物身份读取，不扩展为任意文件读取      |

该表约定操作语义，不声称具体参数语法已发布。输入所需语义包含 API
版本、caller、target、workspace、任务范围与验收条件；返回包含可准确
查询/续接的任务及会话身份、能力限制、结果和产物引用。完整 DTO 与错误
编码以 ai-mcp 模块设计为准，薄 client 不维护第二份业务 schema。

MCP 建议工具为 `agent_bridge_engines`、`agent_bridge_preflight`、
`agent_bridge_start`、`agent_bridge_get`、`agent_bridge_list`、
`agent_bridge_events`、`agent_bridge_continue`、`agent_bridge_cancel`、
`agent_bridge_artifacts`、`agent_bridge_artifact_read`。例如 start/get 与
CLI 对应操作调用同一 application 服务；watch/events 的传输形式可以
不同，任务语义、错误与权限判定保持一致。

易用性应来自明确目标和稳定操作：先给出可用引擎及限制，保留 ID，返回
可以直接查询的身份和产物；错误说明用户可以如何补齐或重试。薄 client
不能静默安装 Bridge、修改全局配置、替换 target，或将失败退化为任意
shell 执行。安装与认证由用户按外置工具原生方式完成。

## 8. 三宿主兼容策略

| 宿主                    | 首版候选交付                                               | 必须证明的真实能力                                              |
| ----------------------- | ---------------------------------------------------------- | --------------------------------------------------------------- |
| Claude Code（`claude`） | 原生技能包，调用外置 BridgeCLI                             | 插件加载、明确自然语言/显式入口、CLI 可用、结果返回发起 session |
| ZCode（`zcode`）        | 原生技能包，调用外置 BridgeCLI                             | 对应入口与权限、独立派发和准确续接；不复用 CodeVow Agent 行为   |
| Codex（`codex`）        | skills-only 技能包及生成的 openai.yaml，调用外置 BridgeCLI | 自然语言加载正负例、CLI 权限、准确任务绑定和结果返回            |

首版只在独立持久会话及准确 ID 续接实测通过后声明可用。桌面窗口出现、
应用内会话展示和 UI 控制分别后续验证，不将 headless 成功描述为桌面
可见。三个引擎分别记录能力，不伪造完全一致。

原生 MCP profile 是后续路径：需要对应宿主真实发现配置、启动 server、
认证、权限及工具调用的证据，以及独立的发布规则审查。当前公共
[`metadata.validate_listing`](../../tooling/plugin_tools/release/metadata.py)
对 Codex skills-only 拒绝 MCP 清单/资源，本稿不修改限制，也不声明现在
已支持 MCP。普通白名单资源打包不能绕过该发布检查。

## 9. 测试、门禁与交付阶段

本轮只完成设计文档，并检查链接、占位、范围及一致性。后续实施分层推进：

| 阶段                | ai-code 交付                                 | 验证门槛                                                       |
| ------------------- | -------------------------------------------- | -------------------------------------------------------------- |
| 契约对齐            | 确认技能输入、窄触发和 Bridge API 消费方式   | 与 ai-mcp 的 DTO、引擎 ID 和错误语义一致，不在插件另建状态机   |
| 有效 RED 与最小插件 | 独立技能、参考资料、三宿主适配、受控测试入口 | 先出现有意义的行为失败，再最小实现；环境错误不算 RED           |
| 公共接入            | 真实 product 与 catalog 路径注册             | 源校验、统一门禁、空目录构建、可信源码包检查；兄弟插件哈希不变 |
| CLI 实测            | 对声明宿主/引擎逐项测试                      | 独立会话、准确续接、失败恢复、权限、返回证据及正负触发         |
| 后续 MCP / 桌面能力 | 独立支持说明及必要 profile                   | 每项有对应真实宿主证据才扩大声明                               |

技能契约测试重点是误触发、目标保留、同引擎明示许可、准确续接、授权
标记无效、结果验证边界和接口一致性，不用仅文件存在断言代替行为测试。
薄 client 如加入，应以受控 Bridge fixture 验证编码、错误传递和重试身份。
运行时状态机、进程、恢复与引擎驱动测试归 ai-mcp，本仓库做消费者侧契约
与必要集成验证。

正式接入的统一门禁是根 `npm test`；源校验使用
`python3 tooling/plugin_tool.py validate --plugin ai-agent-delegation`；
构建使用新空目录并选择声明宿主，包检查以可信源码仓库为 `--root`。
这些命令是后续插件存在后的验证要求，本轮没有执行，也不适用于尚未
注册的设计 ID。

真实验收材料记录宿主/引擎版本、包哈希、task/session 身份、命令结果和
产物证据，支持状态在验收前写 `unverified`。设计稿、通过的静态检查和
Agent 输出均不构成安装、Git 提交或发布授权。
