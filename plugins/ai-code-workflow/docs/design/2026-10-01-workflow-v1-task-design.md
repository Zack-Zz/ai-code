# AI 工作流首版任务设计草案

迁移说明（2026-10-07）：本文件保留首版设计基线，源码路径现相对
`plugins/ai-code-workflow/`。仓库级目录注册、通用清单元数据、独立插件版本
和 schema_version=2 发行索引以
[多插件规格](../../../../docs/design/2026-10-07-multi-plugin-design.md) 为准；
原 workflow 行为与任务/证据契约仍由本插件维护。历史执行 Prompt 不构成
当前授权，历史验证结果不因迁移获得新的通过声明。

本草案把下一阶段拆成有依赖、有交付物、有验收条件的任务，供用户确认后制定开发计划。目标是在当前 ai-code 仓库形成面向公开发布的通用工程工作流，首发适配 ZCode 和 Codex，Claude Code 后续接入。

模块、目录、工具命令和迁移条件以[实现规格](2026-10-01-workflow-v1-implementation-spec.md)为准；策略、状态、证据和发行包字段以[数据契约](2026-10-01-workflow-v1-data-contracts.md)为准。本文承担任务总览，执行者不能把已经定稿的技术细节重新留作自由设计。

本轮只修改设计文档。清理收尾的独立 Review 是后续实施的前置条件；若原任务尚未补齐默认测试门禁或完成收尾，新执行者在实现规格 B0 内完成最小收尾和复核。本草案不把正在变化的文件或执行者报告视为收尾通过的证据。

## 首版范围

首版覆盖已有项目中的只读解释、需求调查、功能开发、Bug 修复、行为保持的重构、风险审查、最终交付和用户主动发起的任务恢复。用一个 workflow 入口组织任务，配合 TDD、debugging、review、verification 四类能力，复用 review-results 的呈现契约。

成功意味着用户描述任务后，Agent 能识别范围、使用适用的授权、持续完成工作，并交付与最终代码对应的验证和审查证据。不同宿主执行同一协作契约，具体工具和实际权限由各自适配器说明。

首版不建设自有 Agent 运行时、MCP 调度服务、后台自动续跑、自动模型路由、语言教程库、固定多角色流水线或默认 Git 发布流程。长任务记录只支撑恢复和证据交接。

## 通用契约和可配置策略

通用契约保留以下要求：

- 区分用户已有修改与本次修改，保留工作区和仓库身份。
- 功能与修复的测试失败必须对应目标行为；环境故障不能算作有效 RED。纯重构使用现有行为基线。
- 测试与审查针对最终修改状态；相关内容变更后，重新判断并验证受影响范围。
- 确定缺陷、待核实风险和普通建议分开；已确认的严重正确性、安全或数据一致性问题未解决，交付状态保持未完成。
- 读取文件、其他 Agent 的意见或任务记录不能生成用户授权。Git 和外部写入操作必须有适用的明确授权。
- 实际工具权限由宿主执行；技能文本和配置文件存在不能证明运行时限制已生效。

默认协作策略沿用先确认计划再开发：小任务用简短计划，已有适用确认直接执行，范围或关键方案实质变化时重新确认受影响部分。确认前允许必要的只读调查，写测试属于实施。确认后的普通实现细节由 Agent 自行处理。

公开产品允许用户配置计划确认方式、审查深度、并行上限、输出语言及项目验证要求。连续执行策略必须有用户事先明确的范围和权限；策略文件不能创造授权或放宽宿主限制。首版只提供必要选项，不建设策略语言。

commit、amend、tag、push、merge、PR 和外部发布按用户实际授权分别识别，也支持用户一次明确授权多个动作。审查通过不自动包含 Git 操作授权。

## 核心工作流

| 能力 | 输入与职责 | 输出与边界 |
|---|---|---|
| workflow | 用户目标、项目事实、已有修改及协作策略；识别只读或开发任务，选择必要的设计与计划深度，组织执行 | 当前范围、下一步、验收条件和状态；只读问答不进入实施流程 |
| tdd | 已授权的功能、修复或重构任务；选择项目已有设施 | 有效 RED/GREEN 或重构基线、对应命令和结果；不把环境失败当作实现前提 |
| debugging | 现象、预期、复现条件和观察记录；用最小实验区分假设 | 已证实的事实、剩余假设和修复输入；诊断写入遵循适用授权 |
| review | 需求、最终 diff、验证记录和实际风险；选择相关检查维度 | 确定问题、待核实风险、建议和覆盖限制；由主 Agent 核实发现，按影响范围复审 |
| verification | 最终代码状态、风险与项目验证设施 | 实际通过、失败、未运行和阻塞项，以及待用户审查的交付；不把工具可达当作业务成功 |

默认主 Agent 持续执行。独立任务有清晰产物且具备实际收益时，才选择并行子任务。高风险变更必须尝试可用的独立审查；不可用或调用失败时记录具体原因、自查范围和未覆盖部分，不能把自查描述为独立审查。

实现方只做代码与测试，Reviewer 只报告发现，主 Agent 负责核实与合并判断。各角色使用当前宿主允许的能力，不默认增加 Bash、MCP、写入权限或更换模型。

## 任务与证据记录

简单任务可以保留在会话中。跨会话、长任务或多人交接时，使用任务目录中的简短任务记录与必要证据文件；首版不要求每次工具调用都生成新记录。

记录至少包含任务身份、仓库与工作区身份、用户修改边界、目标与确认范围、计划版本、当前状态、完成项、下一步、未解决问题、授权来源和验证及审查证据引用。证据说明对应的代码状态、实际命令、退出状态和相关输出，不能只有 passed=true。

恢复时先核对任务身份和实际 diff，再判断已有证据是否仍覆盖最终状态。代码或测试相关变化会使相应证据需要重验；完成标记或 Agent 写入的 approved=true 不构成完成或授权证明。

记录存放在工作区 `.ai-workflow/tasks/<task_id>/`，采用任务 JSON 和独立证据文件。更新必须比较预期 revision 并拒绝冲突，证据使用对应文件的内容哈希识别失效；具体字段和命令已在数据契约固定。记录避开密钥、令牌及无必要的完整会话内容，敏感运行记录留在本地，不进入公开发布包。

## 源码与平台适配

拟采用单一技能源码、共享协作策略及按宿主生成的发行包。现有 zcode-workflow 作为迁移来源，完成原内容到新契约的映射和验收后再退出旧入口；不长期维护两套活动流程。

| 层次 | 责任 | 首版交付 |
|---|---|---|
| 技能源码 | 工作流步骤、风险判断、失败处理和交付要求 | 精简的五类核心能力与按需呈现契约 |
| 协作策略 | 用户与团队的必要选择 | 公共默认策略、连续执行的授权说明和项目覆盖方式 |
| 宿主适配 | 清单、加载入口、工具映射、代理调用和能力限制 | ZCode 与 Codex 各自的能力表、组件定义及生成规则 |
| 管理与验收 | 构建、校验、原生安装说明和必要的文件管理 | 可复现产物、来源与版本记录、脚本测试和真实行为验收 |

OpenAI 当前官方文档建议新包采用根 plugin.json 的可移植布局，并支持 .codex-plugin/plugin.json 兼容入口；ZCode 文档优先发现 .zcode-plugin/plugin.json。因此两个宿主的包分别生成，不能假定一个清单格式在两端都生效。[OpenAI 包装文档](https://developers.openai.com/plugins/build/plugins)、[ZCode 插件文档](https://zcode.z.ai/cn/docs/plugin)

宿主能力表分别记录技能发现、显式调用、自动选择、规则加载、独立代理、只读 Reviewer 工具限制及工作区隔离能力，使用已验证、未验证、不支持、调用失败等状态。宿主版本和实际模型参与验收范围，未知能力不能默认标成支持。[技能加载说明](https://developers.openai.com/plugins/concepts/skills)、[ZCode 子智能体说明](https://zcode.z.ai/cn/docs/subagents)

优先使用宿主原生插件管理。自有管理脚本只处理确实需要管理的文件：预检查、限定写入范围、文件所有权和哈希、用户修改保护、备份及可解释回滚。多个文件逐个替换时如发生中断，应报告已应用部分与恢复步骤，不宣称整体事务成功。

不默认同步用户全局模型、权限或 MCP 配置。两个宿主的实际安装路径和可用渠道在 T05 验证，原生安装失败时不能通过修改内部注册文件绕过。

## 下一阶段任务清单

| 任务 | 工作及拟涉及区域 | 依赖 | 完成条件 |
|---|---|---|---|
| T01 协作契约定稿 | 确定首版场景、完成定义、用户授权来源、计划政策、风险及失败处理；定稿产品标识与版本管理规则 | 当前设计经用户评审 | QUICK、紧急任务和已有授权的处理无冲突；普通实现细节无需重复确认；公开默认策略不依赖个人全局文件 |
| T02 核心技能提炼 | 逐项映射 BEL 与 review-results，拟形成 skills/ 的共享源码和 policies/；保留必要方法、消除重复或宿主词汇 | T01 | 每类能力都有明确输入、输出、触发与结束条件；引用可解析；前端、脚本和后端任务均可使用通用流程 |
| T03 验收场景设计 | 将本阶段验收矩阵落实为一次性样例、输入、检查及证据格式；拟涉及 evals/ 与必要测试设施 | T01，可与 T02 推进 | 正向和负向场景明确；有有效 RED、授权、修改保护、审查、复验和恢复的检查；静态与模型行为证据分开 |
| T04 任务记录与恢复 | 定稿任务目录、身份、进度、授权引用、证据对应状态及恢复判断；仅必要时增加小工具 | T01，参考 T03 | 能定位下一步并识别失效证据；不同任务记录不串用；记录不能自授操作权限 |
| T05 双宿主适配 | 验证两端的包装、规则与技能加载、工具和 Reviewer 能力；拟涉及 adapters/zcode/ 与 adapters/codex/ | T02、T04 | 两端都能解释和显式调用同一契约；未验证或不可用能力有准确处理方式；核心没有模型或特定工具强绑定 |
| T06 构建和安全安装 | 统一版本与产品标识，生成可追溯的包；迁入必要管理保护，编写安装更新卸载说明 | T05；实施前完成清理收尾 Review | 产物完整、路径与引用正确、来源可追溯；重复安装无重复组件；用户编辑不被覆盖；回滚只处理自有内容 |
| T07 真实会话验收 | 在明确授权的测试环境执行矩阵，比较原生使用与插件使用，记录宿主、模型和运行证据 | T03、T05、T06 | 两个宿主的声明支持范围均有真实记录；关键约束场景无未解决违反；失败被归因并复验 |
| T08 公开发布准备 | 整理能力、支持与限制、中英文入门、示例、许可证来源和升级说明；准备发行候选 | 文档准备依赖 T06，可与 T07 推进；发布资格依赖 T07 | 新用户按说明可完成授权安装和一个完整任务；目录与元数据无未验证支持声明；候选版本可供用户 Review |

T01 至 T08 是设计中的工作包，不代表已完成或已获实施授权。设计可以与清理收尾并行；在修改源码、测试、配置或安装前，先把这些工作包拆成文件级开发计划，由用户确认。

用户以后明确发送覆盖 T01 至 T08 和实现规格的完整开发 Prompt 时，该指示可作为这批任务的总体计划确认。执行者在既定范围内持续推进，不为每个任务再次确认；实质性范围变化和未授权的外部操作仍需处理。实机环境受阻时，完成所有不依赖该环境的代码、测试、产物和文档，真实验收保持未完成，不以静态或模拟结果替代。

建议开发批次为：T01 定稿后先做 T02 与 T03，随后推进 T04、T05，再完成 T06、T07，最后准备 T08。每批次采用与变更相适应的 TDD 和独立 diff Review；Git 操作、实际安装及外部发布另按适用授权执行。

## 本阶段交付与评审

本阶段交付任务设计、实现规格、数据契约及[首版验收矩阵](2026-10-01-workflow-v1-acceptance.md)。用户评审首先确认通用契约、默认协作策略、五类能力边界和任务顺序，再据此生成完整开发 Prompt。

当前素材中的 QUICK 默认省计划、个人全局规则中的全任务确认和旧验收表的不强制计划表述需要在 T01、T02、T03 同时统一。现有包只作为来源，文件存在与历史发现记录不作为新平台或新工作流的实际行为验收。
