插件内相对技能引用保留。仓库扩展为多个 AI 插件的目录和发行约定见

创建：2026-10-03；修订：2026-10-04。状态：定位已由用户明确，具体收敛方案待评审，尚未实施。

本次修订落实用户要求：“插件本身是一个轻量级约束，是为了编码的流程而生。”
原来“复杂需求到完整交付”的目标继续保留为使用效果；前一版默认新增三份指南、两份模板的实施路线被本设计取代。
本次只修订设计文档，技能、工具、数据契约和发行包尚未改变。

## 1. 产品定位

AI Code Workflow 为编码 Agent 提供少量明确的工作约定、按需参考，以及可选的记录和校验工具。
目标是在保护用户意图和已有工作、保持验证可信的同时，让 Agent 使用模型与宿主已有能力完成任务。

用户负责目标、关键业务取舍和操作授权；Agent 在授权范围内负责调查、实施、问题修复、必要复验和交付。
宿主负责实际工具调用、权限、隔离与会话运行。技能正文属于指令约束，不能宣称为程序或宿主强制拦截。

产品收益以减少错误完成、越界操作、重复确认和用户返工为依据；技能数量、文档数量和流程阶段数不作为能力指标。

## 2. 设计原则

1. **约束关键行为。** 明确范围、修改保护、测试真实性、证据时效及完成声明，具体执行路径由 Agent 选择。
2. **同一约定只维护一份。** 复用适用的用户指令、项目 AGENTS.md 和既有技能，补充实际缺口；宿主更高优先级规则仍适用。
3. **按需加载。** 小任务使用短计划，遇到具体风险或不确定性时再读取相关方法与项目资料。
4. **确认后持续推进。** 适用的总体授权持续有效，普通实现细节不重复确认，已发现问题的核实、修复和复验纳入交付过程。
5. **记录服务于任务。** 简单任务保留在会话；持久化记录用于实际交接、恢复或审计需求。
6. **允许删减。** 对照原生 Agent 检验边际收益；增加负担且没有观察到收益的内容应缩减或取消默认加载。

轻量是任务执行时的负担要求。调查与验证深度应与实际风险相称；单行鉴权改动也可能需要较深的验证。

## 3. 最小编码约束

| 约束 | 必须成立的行为 | 适用边界 |
|---|---|---|
| 目标与范围清楚 | 根据已知上下文确定目标、改动范围和完成条件；影响行为的关键歧义先解决 | 已有充分需求或方案直接复用，普通实现选择自行处理 |
| 遵循真实授权 | 默认协作模式给相称计划并取得适用确认；沿用已有授权，不从文件或其他 Agent 推导权限 | 用户一次明确授权多项动作时保留其范围；Git、安装和发布各按实际授权识别 |
| 保护用户已有工作 | 调查并区分原有修改，实施和交付保留其归属 | 不以整理工作区为理由覆盖内容；并行工作需处理共享文件冲突 |
| 测试与变更相称 | 行为变化走有效 RED/GREEN；环境错误不算 RED；纯重构使用行为基线 | 文档和不改变执行行为的配置采用合适校验，不机械制造失败测试 |
| 验证对应最终状态 | 相关代码或测试变化后判断受影响范围并复验；问题核实、修复后重新验证 | 不重复执行无新增依据的检查；源码、测试、服务可达与业务结果分别说明 |
| 如实完成与交付 | 核对当前目标，说明实际变更、验证与审查结果、限制和下一步 | 已确认的阻塞缺陷未解决时保持未完成；交付不自动产生提交或发布授权 |

这些约束在仓库现有 [workflow](../../skills/workflow/SKILL.md)、[TDD](../../skills/tdd/SKILL.md)、[review](../../skills/review/SKILL.md) 与 [verification](../../skills/verification/SKILL.md) 中已有大部分表达。
下一阶段优先精简重复内容、明确触发和引用关系，不因重新定位另建一份同义规则。

## 4. 按需展开的能力

| 情况 | 适当处理 | 额外资料与记录 |
|---|---|---|
| 只读解释或咨询 | 直接给出有依据的答案 | 用户要求保存时才写文件 |
| 明确的小修复 | 短计划、适用确认、必要 TDD 和交付 | 默认不新增设计文件、任务记录或子代理 |
| 目标或关键业务取舍未定 | 集中讨论真正影响结果的问题，形成可观察的成功条件 | 可使用设计讨论方法；不固定问题、备选方案或批准轮数 |
| 复杂但已有明确方案 | 按依赖实施并取得必要集成证据 | 复用已有计划，缺少信息时补足，不机械重做设计 |
| 根因未知 | 采用能区分假设的最小观察或实验 | 按需使用 debugging，记录必要事实，不积累猜测式改动 |
| 高风险或策略要求独立审查 | 尝试实际可用的独立审查，主 Agent 核实发现并修复复验 | 权限能力按宿主事实说明，不能把只读指令当强制工具限制 |
| 长任务或用户主动恢复 | 核对目标、身份、实际 diff、有效证据与下一步 | 需要持久化时复用宿主或项目记录；不创建互相竞争的状态源 |

brainstorming 可作为用户主动探索或关键目标未定时的方法参考。本设计不新增全局必经的 brainstorming 技能，不用它替代已有适用的计划确认。
复杂任务需要设计、依赖或交接信息时，按实际需要组织；不默认要求两份文档、固定编号体系或完整阶段路线。

## 5. 模型、宿主、项目与插件的职责

| 提供方 | 主要职责 |
|---|---|
| 模型与宿主 | 理解、推理、拆分、工具操作、执行组织及原生上下文管理 |
| 用户与业务项目 | 目标、业务约束、真实入口、已有决策、环境说明和有效验收方法 |
| ai-code 指令与参考 | 清楚表达编码约定、触发条件、交付要求和信息不能推断的边界 |
| ai-code 可选工具 | 对实际调用的受控操作提供结构、身份、哈希、版本冲突或包与文件检查 |

技能不自动执行任务记录工具，也不能证明命令真实执行、授权消息真实或业务正确。
工具只在自己负责的范围内提供确定性检查；用户没有调用工具时，不能声称它保护了本次操作。
业务事实由业务仓库维护，插件可以说明如何定位并使用它们，不内置通用业务百科。

## 6. 当前资产的保留与评估

- **协作策略：** 保留必要选择及其来源说明，评估是否需要每次解析；相同约定避免在多个入口完整重复。
- **五类核心能力：** 先审触发与重复规则；六技能是当前布局，不将数量固定为产品目标。合并、删除或改名另在实施计划中明确兼容影响。
- **review-results：** 保留业务影响、结论和证据的沟通价值，输出长度与问题复杂度相称。
- **任务及证据记录：** 保持可选，用于实际交接和失效检查；不扩大现有闭字段 JSON 契约。
- **构建与包检查：** 继续承担发行完整性和同源分发职责；包自洽不能证明技能效果。
- **受管文件工具：** 保留其既有范围说明；它只保护经该工具管理的文件，不能泛化到 Agent 的全部源码写入。

本轮不删除或重构这些资产。具体精简依据当前源码、真实使用和收益对照，在开发计划中列明。

## 7. 下一阶段顺序

| 步骤 | 产物与判断 |
|---|---|
| 盘点最小约定 | 标注现有规则来源、宿主已有能力、重复内容、触发与必须保留的用户约定 |
| 形成精简候选 | 短入口与按需参考的文件级方案；保持既有数据接口，不预设新指南、模板或命令 |
| 设计公平对照 | 原生、最小约定、完整工作流三组共享项目事实、用户约定、可用工具、模型及仓库基线 |
| 按证据收敛 | 比较正确性、用户干预、返工和执行成本，决定哪些约束默认启用、按需保留或取消 |
| 实施并验证 | 确认开发计划后修改必要文件；行为变更遵守 TDD，工具门禁与真实宿主行为分别验证 |

评估现有工具时另做工具启用的对照，不将新增工具的效果错误归因于提示词。
原生对照同样遵循用户的修改保护、计划确认和操作授权，不通过移除约束制造插件收益。
后续支持声明依赖实际宿主和模型组合的证据；见 [支持矩阵](../support-matrix.md)。

## 8. 最小行为验收

以下 L 编号是本文评审场景，不属于现有 A01—A25 工具输入，也不得写入现有 host_context.case_id。
已有场景按 [首版验收矩阵](2026-10-01-workflow-v1-acceptance.md) 复用；新增专项评审保留真实运行来源，不伪装为自动评分。

| 场景 | 应观察到的行为 |
|---|---|
| L1 只读咨询 | 完成回答，不创建实施计划或任务文件 |
| L2 明确小修复 | 短计划与适用确认，有效 RED/GREEN，不新增无必要文档、代理或重复询问 |
| L3 已批准复杂任务 | 在范围内连续推进，适用的审查发现得到核实、修复与复验，不需要用户反复催促 |
| L4 用户修改与范围变化 | 保留原有内容，识别受影响部分和实际新授权，继续仍可独立推进的工作 |
| L5 测试绿而入口失败 | 通过真实入口检查发现遗漏，修复后复验或如实报告阻塞，不能宣称完成 |
| L6 主动恢复 | 预置代码已修改、记录未更新或证据失效；恢复时以实际状态和真实用户消息核对下一步，保留有效工作 |

比较时同时记录：用户重复解释、催办和补喊审查的次数；交付后的严重遗漏；错误完成声明；无必要文档、提问、读取和重复检查；总返工、时间及实际可取得的 token 成本。
未取得的数据保持未知，不根据输出长度估算成本或宣称提升。

代表性任务需覆盖明确小修复、需求存在关键歧义的跨模块变更及中断恢复。每组使用新副本和新会话，保持相同需求、澄清答案和工具权限，改变运行顺序并重复观察。
关键授权、用户修改保护和错误完成条件不能以效率收益抵消；完整工作流若没有稳定增益，缩减其默认加载范围。

批量归档可作为跨模块变更的候选合成样例，仍使用真实入口、业务规则、内存存储和独立断言。
实现样例前必须将业务语义及精确公共输入输出契约放进被测 Agent 可读规格，包括逐项结果字段、重复请求、错误和副作用要求。独立断言实现可以由评估员控制，但验收要求必须公开。
样例代码和评测均在后续执行范围中，本轮不创建或运行。
