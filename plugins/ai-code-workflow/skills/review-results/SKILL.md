# Review Results

把审查证据转换成读者可以直接决策的结果。保持技术结论准确，但先解释业务链路、用户影响和下一步，再展示实现细节。跟随用户语言；用户使用中文时，正文使用中文。

## 输出契约

按以下顺序输出：

1. **一句话结论**：`可以合并`、`修改后可以合并` 或 `暂时不能合并`，并说明最主要原因。
2. **结果概览**：列出阻塞、应修复、可选优化的数量，以及必须处理的问题编号。
3. **问题详情**：先阻塞项，再应修复项，最后可选优化项。每个问题使用下方的问题视图。
4. **已确认正常**：只列实际检查过且有证据的关键项。
5. **范围与限制**：说明审查范围、未验证内容和未运行检查。
6. **下一步**：明确是修复、复审还是继续交付。

没有发现问题时也要给出结论、已确认正常和范围与限制；“未发现问题”不等于证明没有风险。

## 问题视图

每个问题依次包含：

1. 业务场景和入口。
2. 从入口到用户结果的完整业务链路。
3. 用 `← 🔴 异常节点` 标出错误首次产生的位置。
4. 异常节点后立即放主要可点击代码链接。
5. 用户感受和业务影响。
6. 是否阻塞、修复目标和验证边界。
7. 其他关联代码、测试和技术证据放入折叠区。

正文中的主链接必须是**问题产生位置**，并使用可点击的绝对文件路径和行号。链路使用 Markdown 引用或普通正文，不使用代码围栏；代码围栏中的 Markdown 链接无法点击。不要把主链接藏到文末证据区。

随后用简短字段收口：

- **用户感受**：用户实际看到或遭遇什么。
- **业务影响**：对流程、数据、安全或运营的后果。
- **处理结论**：阻塞 / 应修复 / 可选优化。
- **修复目标**：描述修复后必须成立的行为，不规定不必要的实现。
- **验证边界**：列出正常、异常和回归场景。

跨多个位置时，在 `<details>` 技术细节中区分：

- **业务入口**：从哪里触发。
- **问题产生位置**：直接导致错误的代码。
- **影响扩散位置**：错误如何传播到其他层。
- **缺失测试**：本应拦住问题的测试文件或场景。

## 严重性与动作

| 原始等级 | 面向读者的动作 | 合并结论 |
|---|---|---|
| CRITICAL | 阻塞 | 暂时不能合并 |
| HIGH | 阻塞 | 暂时不能合并 |
| MEDIUM | 应修复 | 明确记录处理决定后再继续 |
| LOW | 可选优化 | 不阻塞 |

如果项目已有更严格的门禁，使用更严格规则。不要仅根据标签判断；证据显示会造成安全问题、数据错误或核心流程失败时，必须提升为阻塞项并解释原因。

## 写作约束

- 结论先于技术细节，不以优点或过程叙述开场。
- 一条问题只描述一个根因；相同根因的传播位置合并展示。
- 使用业务语言解释术语，避免只写 HTTP、CAS、NPE、race condition 等缩写。
- 修复建议说明目标，验证边界说明怎样证明问题已解决。
- 文件链接必须紧跟对应节点；关联证据才进入折叠区。
