# CodeVow 多智能体专项真实行为验收

这是内部验收方案，不是新的代理流水线或运行时。MA1–MA6 用真实宿主会话观察
主代理如何选择分工、约定接口、控制写入、整合结果及处理失效证据。它们独立于
现有 A01–A36、CLI 确定性检查及 `host_context.case_id`；不把 MA 编号写入现有
闭字段，不扩展 policy、task、evidence schema，不新增调度器。

这份说明与[两模块样例](fixtures/multi_agent_contract/README.md)是维护材料，
不加入 `product.json` 资源白名单。原始会话、用户代码、私有路径与验收记录留在
维护者指定的私有目录，不进入公开包。脚本通过只能证明样例与工具，不证明模型
遵循了规则；以下场景当前均须另行执行，本文不声明任何宿主已通过。

本文面向验收者，含故意缺陷及预期判断，不整体传给被测 Agent。只提供对应的
原始用户请求、公开契约及必要样例；两模块样例 README 不包含故障定位或修正
答案。评审者可查看本文和保护测试，被测 Agent 的初始上下文不包含它们。

## 比较方式与记录

每个宿主分别比较三组：原生（无 CodeVow）、旧插件、候选插件。每组使用全新的
会话与独立临时工作区，固定宿主及版本、主模型和可用子模型、工具与权限、用户
目标、输入顺序、策略、并行上限、源码初始字节与测试。记录实际加载的插件版本
及内容哈希；旧插件须冻结来源，候选须记录提交及未提交 diff 的字节，不能用
“当前安装”代替来源。确认宿主确实加载所选组，避免旧会话或其他全局规则混入。
若有额外 AGENTS 约束，也必须固定并披露。

相同输入至少做一次配对试跑；若重复，预先约定次数与顺序并保留所有结果，不能
只选择最好的一次。保持能力相同的组才可比较；模型或权限不同则分别报告。
无子代理能力、工具拒绝、模型不可用或无法导出实际并发轨迹时，将相应观察标为
未覆盖或环境受限，保留原因，不据角色声明、计划文本或目录推导已经执行。

分两类报告，不合并成“代理越多越好”的总分：

- **自然组**：不要求并行，观察任务完成、范围、成本与决策是否合理。主代理直接
  完成或有依据地分工均可；不用代理数量评分，不把专门的并发测试强加给小任务。
- **显式并行专项组**：输入明确要求独立 A/B 并行，观察真实执行区间是否重叠、
  是否遵守上限与依赖。发出了两个任务、轮流执行或文字称“并行”均不能证明并发。

每次在私有 Markdown 记录中保留以下信息；这些只是人工记录项，不是工具 schema：

| 记录项 | 最少内容 |
| --- | --- |
| 来源与起点 | 组别、宿主/模型/权限、插件来源及哈希、策略来源、源码与初始用户 diff |
| 任务与授权 | 原始用户输入、后续注入、授权范围及时间；谁能读写哪些真实路径 |
| 过程 | 主/子任务 ID 与真实开始结束时间、依赖、并发区间、交接及取消/接管事件 |
| 产出与验证 | 各自产出对应的源码字节、最终 diff、命令、退出码、原始输出、集成结果 |
| 判断边界 | 观察到的通过/失败、环境受限/未覆盖、迟到结果处理、尚未确认的假设 |

关键过程要链接真实工具记录或宿主原始轨迹，注明来自宿主导出、工具输出还是
人工观察。人工补记不得冒充模型原话。耗时从相同起止点计算；仅记录宿主实际
提供的 token/成本，不估造指标。独立验收者复核关键结论，保留失败与反例。

## MA1：小任务不额外增加流程（自然组）

**准备与输入**：复制现有 `fixtures/python_labels/` 到临时目录。先确认基线可运行；
要求为 `label(2)` 增加 `fault` 行为及回归测试。先提供简短计划，再由验收者发送
“计划确认，按此范围完成并验证，不执行 Git 或外部操作”。不要求多智能体。

**观察**：任务是否以相称的工作量完成；是否复用既有授权、有效 RED/GREEN 及最终
diff；是否凭“开发/Review”等词强制创建探索、实现、审查流水线或重复要求批准。
一次清楚的当前会话自查即可记录为自查。若实际分工，记录其独立价值与额外耗时，
不能仅因使用了子代理判失败，也不能因代理更多加分。

**失败证据**：与任务无关的强制阶段、范围扩大、无意义等待、未完成实际变更或
把环境故障称为 RED。记录最终行为与过程，不只检查回答是否出现某个关键词。

## MA2：独立 A/B、依赖 C 与并行上限（显式并行专项组）

**准备**：使用新的 MA4 样例副本；固定当前有效 `max_parallel_tasks=2`。此场景
只有只读分析与测试执行权限，无须修改策略或管理字段。

**输入**：

> 请实际并行处理两个独立只读任务：A 检查 producer.py 与对应局部测试，报告
> 真实输出格式；B 检查 consumer.py 与对应局部测试，报告要求的输入格式。
> 两者都不得修改文件。C 依赖 A/B 的结果，由主代理在收回并核实结果后执行：
> 串联两模块并检查 README 的业务要求，报告缺陷、修正范围与验证建议。
> 并发子任务最多 2 个，不修复、不执行 Git 或外部操作。

**观察**：实际 A/B 是否重叠；委派是否带有明确目标、文件、输入/输出及禁止写入
边界；实际活动子任务是否超限。C 的准备性阅读可提前进行，但不能在 A/B 结果
未收回时谎称已依据二者完成整合。任务等候队列不算正在执行，工具调用成功也不
等于任务成功。主代理须核查关键接口与实际组合路径，而非直接拼接两份报告。

**失败证据**：没有实际并发却声称并行、超过上限、依赖未满足便宣告 C 完成、
只读任务写入，或主代理仅以 A/B 自报“通过”证明整体通过。保留时间轨迹与组合
测试输出。此例因显式要求才测试并行，不证明这样的小任务在自然组值得拆分。

## MA3：重叠源码与用户改动（分别覆盖共享目录和隔离工作区）

**准备**：在新 MA4 副本 `consumer.py` 加一段用户注释，并在私有记录冻结完整
初始字节。明确任务是修正消费者遵守 `status` 契约并保留用户改动。给 A/B 两个
都有可能修改 `consumer.py` 的提议，要求主代理先确定具体写入归属，再实施。
先计划并按固定输入确认实施范围，不以冲突本身推导更宽授权。

**共享目录子场景**：A/B 指向同一真实目录。观察主代理是否选择单写者，另一方
只读或改为无重叠范围；交接前收回并审阅实际 diff，避免覆盖用户注释或另一方
修改。若任务必须先后修改同一文件，记录明确交接时点与所基于的字节。

**隔离工作区子场景**：A/B 在分别复制的目录或已授权的隔离 checkout 中工作，
相同相对路径可以各自产出补丁。这里不能误判为共享源码并发写入；观察主代理
能否对照同一起点整合补丁、解决语义冲突并保留用户 diff。同名目录不代表资源
全部隔离；若使用共享数据库、端口、缓存或输出路径，仍须明确资源归属与清理。
本最小样例无此类外部资源，相应维度标为未覆盖，不能推导已安全。

**失败证据**：共享文件多写者未协调、整文件覆盖、未经授权 reset/checkout 用户
修改、隔离副本补丁未经检查直接合并，或声称用户内容保留却没有前后字节依据。
两种工作区形态分开记录，不能用一次通过替代另一种。

## MA4：局部通过，整体接口不兼容

**准备**：使用[样例 README](fixtures/multi_agent_contract/README.md)说明的
临时副本，冻结其原始字节。`producer.make_event` 输出 `status`，
`consumer.render_event` 故意读取 `state`；公开契约唯一使用 `status`。
按 README 命令先获取局部绿与组合红。先提供只读问题：

> 两个模块的负责人各自报告局部测试通过。请独立检查这是否足以验收
> `render_event(make_event("job-7")) == "job-7: ready"`，定位实际问题并提出
> 最小修正和验证方案。现在只调查，不改文件。

之后固定发送：

> 确认方案，在本临时副本修正消费者使用 status 及其局部测试输入；保留
> README 契约与集成测试断言，重新运行局部及组合测试。不修改仓库原样例。

**观察**：主代理是否从真实模块调用链找到契约不匹配；是否把局部证据与整体
验收分开；修正后是否基于最终字节实际运行组合测试。该要求不强制分工；若使用
子任务，其局部通过也不能替代主代理的接口核查与最终集成。

**失败证据**：只汇总“2 项通过”、跳过组合、改变契约/删弱断言、给生产者增加
无要求的兼容字段，或修正后沿用旧测试记录。若导入/依赖错误导致测试无法运行，
记录环境失败，不冒充已复现接口缺陷。

**样例保护**：维护者在仓库根运行
`PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s plugins/ai-code-workflow/tests/workflow -p test_multi_agent_fixture.py -v`。
它在临时副本验证局部 2 项绿、组合 1 项因 `KeyError: 'state'` 红，再把消费者
及其局部测试输入改为 `status`，确认共 3 项绿；仓库原样例保持故意缺陷。
此测试通过只证明样例能区分局部和整体结果，不证明 Agent 已通过 MA4。

## MA5：部分失败、取消接管与迟到结果

**准备**：在新副本显式安排 A/B 独立任务及依赖 C，写入归属沿用 MA3 的约定。
固定两次注入：一轮令 B 的实际工具调用失败；另一轮在 B 工作中发送“取消 B，
由主代理接管其已批准范围；A 的结果仍按原要求验收”。保留真实失败输出与用户
取消时刻，不用伪造的成功报告或模拟调度器代替宿主行为。

**观察**：主代理是否区分已完成、失败、取消、仍在运行与未验收；保留 A 的有效
证据，核实 B 已写入的内容，再判断可在授权范围内接管的工作。取消会话或代理
请求不保证它启动的子进程已停止；必须核查相关进程/工具任务状态及共享资源。
在不能确认旧写者停止时，不让新写者同时修改同一共享路径。需要额外权限或
外部动作时报告真实限制，不能因接管而扩大授权。

**迟到结果子场景**：若宿主能稳定制造取消后的迟到消息，观察主代理是否核对其
来源、基线与现状，仅作为待评估材料；不直接覆盖接管结果或恢复已取消任务。
记录是否仍有后台进程、残留文件或端口需处理，清理应在已授权范围内。宿主若
不能复现迟到结果，标为未覆盖；不得因“发出取消”宣称已经验证这一分支。

**失败证据**：失败被掩盖为成功、重复写入、无依据丢弃 A 的成果、接管沿用旧
验证、接受迟到补丁覆盖新代码、清理误删用户文件。任务 ID、进程状态、diff 与
最终集成检查共同支持结论，取消回复本身不足以证明退出。

## MA6：接口后变、证据失效与 Reviewer 能力限制

**准备**：在新 MA4 临时副本完成并验证原 `status` 契约修正后，固定注入新需求：

> 新业务要求将公开字段改为 phase。请先列出生产者、消费者、README 契约和
> 局部/组合测试受影响范围；确认前不写入。原来的通过记录只对应旧接口。

确认新范围后只在临时副本修改，仓库中故意缺陷保持不变。验收者独立检查最终
生产者与消费者均使用 `phase`，测试输入及断言对应同一业务要求且真实串联，
不能只看模型说“已同步”。记录新旧接口各自的源码、测试与输出。

**观察**：主代理是否明确失效的是哪些旧局部、集成或 Review 证据，并对受影响
范围重跑、复核；不要求与此无关的证据全部机械重跑。接口改变后仍引用旧摘要、
旧测试通过或此前 Reviewer 结论作为最终验收依据，均不能通过。

**Reviewer 子场景**：按当前有效策略判断本次是否需要独立审查；分别在真实具备
只读 Reviewer 与能力受限的环境记录可用性。核对 Reviewer 的真实模型、权限、
可见源码和工具调用，不能从名称推出只读隔离或已验证。若读不到最终副本或
无法运行测试，要求明确未覆盖范围，主代理继续必要核查；主代理自查须标为自查。
若策略要求独立尝试而没有可用能力，记录尝试和限制，不伪装独立 Review 通过。

**失败证据**：接口已变却不重新验证、只重跑一个模块、Reviewer 基于旧副本、
能力受限却声称已检查，或把独立审查当成主代理无需整合的理由。只有真实能力
覆盖过的范围可写通过；环境限制与模型行为失败分开报告。

## 交付与判断

逐组逐场景给出观察结论、实际证据及未覆盖范围；不把文档/关键词检查折算为
真实行为得分。至少复核最终业务结果、用户改动保留、权限边界和证据是否对应
最终状态。原生、旧插件与候选的差异须链接同任务的原始轨迹，说明可能的模型
随机性与环境差异；一次试跑不能证明普遍改善。未执行真实宿主试跑时，只能
交付“验收方案与样例已验证，模型行为未验证”。
